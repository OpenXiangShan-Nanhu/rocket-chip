# PLIC 安全中断方案总结

## 1. 文档目的

本文根据 `安全中断方案-PLIC.pptx` 内容整理，目标是总结一套面向 `RISC-V PLIC` 的安全中断扩展方案，用于支持 `TEE-OS` 与 `REE-OS` 并存场景下的中断隔离、路由与处理控制。

## 2. 背景与问题

当前方案基于 `PLIC`，并参考 `APLIC sourcecfg` 一类“中断源属性可配置”的思路，为中断系统补充“安全/非安全”维度。

PPT 给出的背景结论主要有两点：

- `x86` 机密虚拟机方案，如 `Intel TDX`、`AMD SEV-SNP`，已经具备安全中断相关支持。
- `RISC-V` 平台侧硬件仍缺少统一、安全中断能力；相关指令扩展和实现方式也尚未形成统一标准。

因此，本方案的核心目标是：在现有 `PLIC` 基础上，以较小改动实现安全中断识别、正确路由、处理中断嵌套约束，以及 `claim/complete` 的安全一致性。

## 3. 方案总体思路

方案从三个层面扩展：

- 中断源属性扩展：为每个外部中断源增加安全属性。
- Hart/Context 状态扩展：为当前执行世界增加可见状态标识。
- `claim/complete` 跟踪扩展：记录“当前正在服务的中断”及其安全属性，避免错误领取、错误完成和重复完成。

从 PPT 内容看，整体设计围绕以下原则展开：

- 非安全中断与安全中断使用 `1 bit` 区分。
- `REE-OS` 中允许处理非安全中断，且可被安全中断打断。
- `TEE-OS` 中允许处理安全中断，且不能被非安全中断打断。
- 路由决策不仅取决于中断是否使能，还取决于中断源安全属性、当前 world state，以及当前 context 是否正在服务安全中断。

## 4. 关键扩展设计

### 4.1 中断源安全属性：`sec_src[id]`

方案引入 `sec_src[id]` 寄存器，用于描述中断源 `source id` 的安全属性。

- `0`：非安全中断
- `1`：安全中断

PPT 中先假设只有 `32` 个外部中断，因此可以按位存储，每个 bit 对应一个中断源的安全属性。

作用是让 PLIC 在中断分发时知道“这个中断属于安全世界还是非安全世界”。

### 4.2 当前世界状态：`world_state[ctx]`

方案引入 `world_state[ctx]`，表示某个 `hart/context` 当前所处世界状态。PPT 里将其描述为每个 hart 的 `world state CSR` 的同步映射。

其作用是支持中断路由判断：

```text
to_S(ctx, id) = (sec_src[id] == world_state_ctx[ctx])
to_M(ctx, id) = ~to_S(ctx, id)
```

可理解为：

- 如果中断源属性与当前世界状态匹配，则可直接路由到当前上下文侧处理。
- 如果不匹配，则需要走另一条路径，或由更高权限进行中转/处理。

### 4.3 有效使能判断

PPT 给出的有效使能关系为：

```text
eff_enable_S = enable_S & to_S
eff_enable_M = enable_M & to_M & ~(sec_busy_ctx[ctx] & ~sec_src[new_id])
```

这说明中断是否最终可投递，不只是普通的 `enable` 判断，还受以下因素影响：

- 当前中断是否该投递到 `S` 或 `M`
- 当前上下文是否正在服务一个安全中断
- 新到来的中断是否为非安全中断

其中：

```text
sec_busy_ctx[ctx]
```

表示当前 `ctx` 是否正在处理安全中断。

## 5. `irq_track[ctx]` 跟踪机制

### 5.1 设计目的

PPT 明确提出，`sec_busy_ctx[ctx]` 不是新增一套独立寄存器组，而是利用 `irq_track[ctx]` 中已有或扩展后的信息推导出来。

方案通过 `irq_track[ctx]` 跟踪一次已领取但尚未完成的中断，既支撑安全中断忙状态判断，也支撑 `claim/complete` 对账。

### 5.2 寄存器字段

`irq_track[ctx]` 结构如下：

```text
31:16  Reserved
15:2   irq_id
1      req_sec
0      in_service
```

字段含义：

- `irq_id`：当前 `ctx` 正在处理的中断号
- `req_sec`：本次处理中断是否为安全中断
- `in_service`：当前中断是否处于服务中

### 5.3 忙状态推导

PPT 给出的关系为：

```text
sec_busy_ctx[ctx] = irq_track[ctx].in_service & irq_track[ctx].req_sec
```

即：

- `in_service = 1` 且 `req_sec = 1` 时，说明该 `ctx` 正在处理安全中断
- 此时新来的非安全中断应被阻塞，不允许错误抢占 `TEE-OS`

## 6. `claim/complete` 语义约束

### 6.1 `claim` 成功后的锁存

当某个 `context` 读取 `claim` 成功后，需要把以下信息锁存到 `irq_track[ctx]`：

- `irq_id = id`
- `req_sec = sec_src[id]`
- `in_service = 1`

这一步的意义是把“这次究竟领走了哪个中断、它是否属于安全中断、是否仍在服务中”固化下来，供后续 `complete` 校验使用。

### 6.2 `complete` 的校验逻辑

根据 PPT，`complete(ctx, id)` 通过校验后，才允许清除 `in_service`。校验至少依赖以下信息：

- 当前必须确实存在服务中的中断：`in_service == 1`
- `complete_id` 必须与已锁存的 `irq_id` 一致
- 安全属性必须与已领取时记录的信息一致

PPT 原文在这一处表达较简略，但其设计意图是明确的：`complete` 必须和之前成功 `claim` 的那次中断严格配对，不能写空、不能乱写、不能重放。

### 6.3 三类安全收益

`irq_track[ctx]` 带来三类直接收益：

- 防重复领取：同一个中断在 `complete` 之前不能再次被当成新中断分发。
- 防空 `complete`：只有 `in_service = 1` 才允许 `complete`。
- 防重复 `complete` / 重放：第一次 `complete` 成功后应清零，后续再对同一 ID 写入应拒绝。

## 7. 中断路由与处理行为

### 7.1 在 `REE-OS` 中处理中断

当系统当前处于 `REE-OS`：

- 非安全中断可直接被处理。
- 安全中断可以打断当前非安全中断处理流程。

从 PPT 表述看，其处理链路大致为：

1. 初始化中断属性与 `world_state[ctx]`
2. 外部中断到来，置位 `pending`
3. 触发相应 `context` 的中断入口
4. `context` 读取 `claim`
5. 结果锁存到 `irq_track[ctx]`
6. 处理完成后，依据 `irq_track[ctx]` 信息完成对账并执行 `complete`

这说明 `REE-OS` 环境下，系统允许“正常处理非安全中断，同时对安全中断保持可抢占响应能力”。

### 7.2 在 `TEE-OS` 中处理中断

当系统当前处于 `TEE-OS`：

- 安全中断允许被处理。
- 非安全中断不能打断当前 `TEE-OS` 执行。

PPT 重点强调：

- 若 `sec_busy_ctx[ctx] = 1`，说明当前正在处理安全中断。
- 若新到来的中断满足 `~sec_src[id]`，说明它是非安全中断。
- 在这种组合下，`eff_to_M` 失败，新的非安全中断不能进入 `pending` 有效处理路径，表现为被阻塞。

这正是方案想要的安全隔离效果：`TEE-OS` 中的安全中断服务不被非安全中断破坏。

## 8. 方案价值

该方案的价值主要体现在以下方面：

- 在不完全依赖新架构标准的前提下，为 `RISC-V PLIC` 补充安全中断语义。
- 用较少寄存器扩展实现中断源属性标记、世界状态感知和处理中断跟踪。
- 通过 `irq_track[ctx]` 把“安全路由”和“claim/complete 一致性”统一起来。
- 明确规定 `REE-OS` 与 `TEE-OS` 下的可抢占关系，保证 TEE 执行期间不被非安全中断破坏。

## 9. 需要关注的实现点

基于 PPT 内容，落地实现时至少需要关注以下问题：

- `sec_src[id]` 的初始化与配置接口如何定义。
- `world_state[ctx]` 与 hart 当前世界切换状态如何严格同步。
- `claim/complete` 的硬件时序与锁存时点需要精确定义。
- 多核、多 context 场景下，`irq_track[ctx]` 的独立性和一致性需要保证。
- “安全中断只能由安全 context 处理”这一静态配置前提，需要在系统配置阶段被强约束。
- 若未来切换到 `APLIC` 或更标准化的中断架构，需评估本方案寄存器模型与软件接口的迁移成本。

## 10. 总结

这份 PPT 提出的本质上是一套面向 `PLIC + TEE` 的安全中断增强机制。其核心做法是：

- 给中断源增加安全属性 `sec_src[id]`
- 给执行上下文增加世界状态 `world_state[ctx]`
- 给 `claim/complete` 增加中断跟踪 `irq_track[ctx]`

借助这三部分，系统能够判断“哪个中断该由谁处理、当前是否允许打断、一次 `complete` 是否合法”，从而实现：

- `REE-OS` 处理非安全中断时可被安全中断打断
- `TEE-OS` 处理安全中断时不被非安全中断打断
- `claim/complete` 不乱序、不重放、不丢对账
